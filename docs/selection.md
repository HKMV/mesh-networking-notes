# 五款 Mesh VPN 方案对比与结论

> 这些都是实际部署过、跑过流量的方案，不是看文档得出的结论。产品迭代很快，
> 具体能力以各自官方文档为准；这里只写跟「选哪个做主用」相关的差异。

## 逐条对比

| 方案 | 协议/实现 | 是否需要中心 | 中继能不能自己搭 | 形态与我的使用状态 |
|---|---|---|---|---|
| **EasyTier** | Rust 实现，去中心化组网 | 不需要中心控制面 | 可以，中继节点自己部署 | **当前主用**。中继自建，客户端覆盖 Windows / Arch Linux / macOS / 路由器 |
| **NetBird** | 基于 WireGuard，控制面与中继分离 | 需要（可自建管理端） | 可以 | **当前备用**。与主用链路双开并存，手动切优先级 |
| **Tailscale** | 基于 WireGuard，自带协调服务与 DERP 中继 | 需要（官方托管，或第三方实现自建） | 可以（DERP） | 实际部署过，未进当前主备结构 |
| **ZeroTier** | 自有协议，支持二层网络 | 需要（根节点） | 有限（可自建 controller / moon） | 实际部署过，未进当前主备结构 |
| **vnt** | Rust 实现，P2P + 可自建中继 | 不需要中心控制面 | 可以 | 实际部署过，未进当前主备结构 |

## 结论

**主用 EasyTier**：在「中继自己搭 + 不依赖外部控制面 + 多平台都能装」这三条上，它是落地成本最低的一个 —— 不用额外维护一套控制面服务，就不会多一个会挂的东西。

**NetBird 做备用**：备用的价值不在于功能更强，而在于**故障域不同**。如果备用链路和主用共用同一个控制面或同一台中继，那主用出事时备用大概率一起出事。NetBird 是独立的一整套，代价是要多维护一份，所以只当备用，不参与日常流量。

**另外三款为什么没进主备**：都实际用过、都踩过坑。它们各自都有能做主的场景 —— 尤其零配置、跨团队共享这类需求 —— 但在「中继完全自控 + 不引入额外中心」这条上，需要额外自建控制面或中继组件才能达到同样的效果，多一套组件就多一份长期维护成本。折下来我选了 EasyTier。

## 一句提醒

选型别只看功能对比表。真正天天折磨人的是穿透失败、中继限速、某个平台装不上、系统更新后网卡起不来这几件事，判断标准应该放在这些上面。

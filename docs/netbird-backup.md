# 备用链路：NetBird 双开并存与手动切优先级

> 备用的意义是**故障域不同**，不是功能更强。所以这两套是并存关系，不是主备自动切换。
> NetBird 官方术语：控制面叫 **Management**，中继叫 **Relay**，网段接入叫 **Networks**（旧的 Routes 已标 deprecated）。

## 官方对这个链路的两个关键说明

- 直连优先、失败才回退：「NetBird always prefers a direct peer-to-peer (P2P) connection and falls back to a relay server when a direct path can't be established.」
- **Signal 不可达时会静默走到中继**：官方原文「If Signal is unreachable, the peers can't even compare notes, and the connection silently lands on the relay.」—— 排查「为什么在走中继」时，先看 Signal 通不通，别只看穿透。
- 走中继仍然是端到端加密的，中继服务看不到内容。

出处：[NetBird · 理解 NAT 与连接](https://docs.netbird.io/about-netbird/understanding-nat-and-connectivity)、[中继排查](https://docs.netbird.io/help/troubleshooting-relayed-connections)。

## 为什么要双开并存

- 两套网络同时在线，任何一套挂了，另一套的连接状态是现成的，不需要「临时装一套」。
- 故障域分开：控制面、中继、客户端进程各自独立，同一类故障不会同时打中两边。
- 代价是多一份配置和一份维护，所以只保留两条，不再加第三条。

## 并存时最先要解决的冲突

| 冲突点 | 处理方式 |
|---|---|
| 虚拟网段重叠 | 两套网络的虚拟网段必须错开规划。网段撞了会出现「一部分能通一部分不通」，比全不通更难查 |
| 两套虚拟网卡 | 系统里会同时出现两块虚拟网卡，路由表里两套路由并存；排障时先确认某个目标 IP 现在实际走的是哪块网卡 |
| DNS 与域名后缀 | 两套网络各自注入的 DNS/域名解析规则要理清，避免解析走错链路导致的「能 ping 通、域名打不开」 |
| 子网路由重复 | 同一目标网段两边都宣告时，实际走哪条取决于路由优先级，必须显式指定，不能靠默认 |

## 手动切优先级

原则：**任何时刻只有一条链路是首选**，切换是「明确的、可回滚的一次操作」，不是状态机。

1. **记录当前状态**：先存一份当前的路由优先级/or 指标值（回滚全靠它）。
2. **提升目标链路**：把要用的那条的优先级调高（更小的跃点/更精确的路由），另一条保留但不作为首选。
3. **验证实际出口**：用路由查询和到目标地址的实际路径确认流量真的换了路 —— 只看「客户端显示已连接」不算数。
4. **不急着关掉另一条**：留着当天的逃生通道，确认新路径稳定几个小时后再考虑停掉。
5. **回滚**：把第 1 步记下的值写回去，重复第 3 步确认。

## 切换后必须确认的四件事

| 检查 | 目的 |
|---|---|
| 路由表里目标网段指向哪块虚拟网卡 | 确认优先级真的生效，而不是只改了配置 |
| 到目标地址的实际路径 | 确认经过的是预期的那套网络，而不是另一套或直连 |
| 是直连还是走中继 | 走中继说明穿透失败，功能能用但体验会明显变差 |
| 业务实际访问 | 至少打开一个真实业务做端到端验证，别停在 ping |

## 为什么不做自动故障转移

自动切换需要可靠的健康判断，而「链路是否可用」本身就很难判断准：中继通了但带宽被压到不可用、控制面在线但对端不在线、路由还在但数据面已经断了 —— 这些都不一定触发得了自动切换，或者反过来误判导致来回跳。手动切换的每一步都能被确认，出问题时责任边界清楚。
